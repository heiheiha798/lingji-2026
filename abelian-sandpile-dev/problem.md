# 阿贝尔沙堆稳定化

## 背景

在雪崩、地震和连锁故障等系统中，一个局部单元越过阈值后，可能只影响附近区域，也可能触发大范围级联。阿贝尔沙堆是研究这类自组织临界现象的经典数学模型，也与概率论中的随机过程、离散拉普拉斯算子和势理论有关。

它不是用来预测某一场真实雪崩的工程模型。它的价值在于：用非常简单、答案严格确定的局部规则，保留“局部触发、动态传播、最终稳定”这一类计算结构。大规模沙堆的活跃区域会随输入不断变化，因此既可以采用规则的全网格计算，也可以追踪稀疏活动区域，这使它成为适合 GPU 算法设计和性能优化的问题。

## 规则与任务

给定一个 `rows x cols` 的二维矩形网格。格点 `(y, x)` 初始有非负整数 `h[y, x]` 粒沙。

当 `h[y, x] >= 4` 时，可以对该格点执行一次倒塌：

1. 本格高度减 4；
2. 上、下、左、右四个方向各发送 1 粒沙；
3. 若某个方向越过网格边界，该粒沙离开系统，不再返回。

不断执行合法倒塌，直到所有格点均满足 `0 <= h[y, x] < 4`。本题采用开放边界，测试数据均保证最终能够稳定。

你需要输出两个数组：

- `stable[y, x]`：最终稳定高度，类型为 `uint8_t`；
- `odometer[y, x]`：格点 `(y, x)` 在整个过程中倒塌的总次数，类型为 `uint64_t`。

### 结果为什么唯一

阿贝尔性质保证：只要每一步处理的格点在当时确实满足 `h >= 4`，不同的合法处理顺序会得到相同的最终稳定状态和相同的 odometer。选手不需要复现参考程序的执行顺序，可以自由组织并行计算。

### 批量倒塌

若某格点当前高度为 `h`，可以一次处理

```text
q = floor(h / 4)
```

次倒塌。处理后本格暂时剩余 `h mod 4` 粒沙，并向每个网格内邻居发送 `q` 粒沙。之后到达的新砂粒仍可能使它再次变得不稳定。

### 边界示例

左上角只有右、下两个网格内邻居。若其高度为 4，倒塌后本格变为 0，右、下邻居各增加 1，另外两粒沙离开网格。

## 样例

初始高度：

```text
0 0 0
0 5 0
0 0 0
```

最终稳定高度：

```text
0 1 0
1 1 1
0 1 0
```

odometer：

```text
0 0 0
0 1 0
0 0 0
```

## 工程与接口

选手修改 `solution/` 下的代码工程，可以自由增加、删除和组织源码。评测脚本会执行该目录的 `Makefile`，并要求最终生成：

```text
build/submission/libsandpile_submission.so
```

动态库必须导出 `interface/sandpile_api.h` 声明的 C 接口：

```cpp
extern "C" int sandpile_run(
    const std::uint32_t *initial,
    std::uint8_t *stable,
    std::uint64_t *odometer,
    int rows,
    int cols);
```

接口约定：

- `initial`、`stable` 和 `odometer` 都是 CPU 内存中的行优先数组；
- `initial` 只读，包含 `rows * cols` 个 `uint32_t` 元素；
- `stable` 和 `odometer` 必须被完整覆写，不能依赖原有内容；
- 选手代码自行完成 CUDA Context 初始化、显存分配、输入上传、GPU
  计算、结果下载、同步和资源释放；
- 函数返回时两个 CPU 输出必须已经可用，不得遗留后台任务继续修改输出；
- 返回 0 表示成功，非 0 表示本次任务失败。

公开基线已经拆分为多个 `.cu` 和头文件，用于展示工程结构，并不限制选手继续拆分文件或修改构建方式。只要 `solution/Makefile` 能按要求生成动态库，评测器不关心工程包含多少文件。

## 数据范围

- `3 <= rows, cols <= 8192`；
- `rows * cols < 2^32`；
- `0 <= initial[y, x] <= 10^6`；
- 总砂量和所有 odometer 值均可由 `uint64_t` 精确表示；
- `stable` 和 `odometer` 均采用整数逐元素精确比较。

## 计时范围

计时覆盖一次完整的 `sandpile_run` 调用，包括：

- CUDA Context 初始化；
- 显存分配和释放；
- Host-to-Device 与 Device-to-Host 传输；
- kernel 启动、CPU/GPU 协调、同步和输出生成。

计时不包含：

- 测试数据生成；
- 动态库构建和加载；
- 参考答案生成与结果比较。

每个性能样本在全新的评测进程中运行，不进行预热，也不复用前一次调用
创建的 CUDA Context、显存或内部状态。

## 测试方式

### 随机功能测试

完整评测首先运行一组随机正确性测试。每次从五种生成模式中产生不同尺寸、参数和种子的中小规模数据，使用 CPU 与 GPU reference 交叉验证后，再与选手结果逐元素比较。

随机测试只输出 `PASS/FAIL` 和用于复现的 suite seed，不输出选手耗时、参考耗时、加速比或分数。失败后可以使用同一个 seed 复现：

```bash
python3 run_judge.py --random-only --random-seed 184725193
```

### 固定性能测试

六个性能点由 `judge/cases.hpp` 中的公开生成器、固定参数和固定种子确定性产生。评测时在线生成输入，并由 GPU reference 在线计算标准输出，不需要保存大型输入输出文件。

每个固定点在 3 个独立进程中各运行一次；每次都精确比较 `stable` 和
`odometer`，性能取 3 次完整任务时间的中位数。reference 也使用相同的
冷启动完整任务口径独立测量。测试点输出正确性、中位耗时、reference
耗时和加速比。

| 编号 | 名称 | 规模 | 分布 | 主要考察 | 评分方式 | 权重 | 目标时间 |
|---:|---|---:|---|---|---|---:|---:|
| 0 | tiny-correctness | 127 x 131 | 小临界区与少量砂源 | 基本正确性 | 正确即得 | 10 | - |
| 1 | global-rain | 4096 x 4093 | 全局稳定背景上的随机降沙 | 稠密活动与规则访存 | 固定目标 | 20 | 260 ms |
| 2 | local-avalanche | 4096 x 4093 | 中心临界区与局部扰动 | 空间局部性 | 开放竞技 | 20 | 不设 |
| 3 | many-sources | 4096 x 4093 | 稀疏背景上的 256 个高砂源 | 原子冲突与动态工作量 | 开放竞技 | 20 | 不设 |
| 4 | near-critical | 2048 x 2039 | 接近临界状态的全局扰动 | 长传播与策略切换 | 开放竞技 | 15 | 不设 |
| 5 | large-mixed | 8192 x 8179 | 四个局部临界区和 32 个砂源 | 大网格与无效访存 | 开放竞技 | 15 | 不设 |

## 评分

任一输出数组不正确，该测试点成绩为 0。正确结果按两组规则统计，名义权重比例为 `30:70`。

### 固定目标组

- `tiny-correctness`：正确即获得 10 权重；
- `global-rain`：占 20 权重，目标时间 `g = 260 ms`。该值在正式 RTX 4090
  环境中按上述冷启动完整任务口径校准。设选手时间为 `t`：

```text
score = 20 * min(1, g / t)
```

### 开放竞技组

其余四个测试点不设满分时间。设该点权重为 `w`，选手时间为 `t`，比赛平台在相同硬件和镜像中测得的公开参考时间为 `r`：

```text
performance_index = w * (r / t)^(1/4)
```

四个点的权重为 20、20、15、15。性能指数不封顶，继续缩短时间会继续增加成绩。四次根用于降低极端倍速对总成绩的支配。公开参考实现在开放组的基准指数为 70，因此最终综合指数可以超过 100。

正式成绩由比赛平台计算。`run_judge.py` 不在本地计算分数；随机功能测试也不产生性能数据。

## 提交内容

个人参赛选手提交完整的 `solution/` 目录，其中至少包括：

1. `Makefile` 和全部求解源码；
2. `optimization.md`，自由说明优化思路；如有额外依赖，说明名称、版本和安装方法；
3. `benchmark.json`，使用最终工程运行完整评测生成的自测记录。

生成自测记录：

```bash
python3 run_judge.py \
  --json-output solution/benchmark.json
```

脚本会写入运行环境、命令、种子、正确性和耗时。该文件由脚本完整生成并覆盖写入，不需要也不得手工修改。它用于复现和性能核对，不代替正式评测结果。

## 公平性与可修改范围

以下内容构成统一接口和评测链路，不属于选手提交内容：

- `interface/sandpile_api.h`；
- `run_judge.py`；
- `judge/` 下的全部文件。

正式复核会用组织者版本覆盖这些文件以及固定测试定义。不得绕过计时、伪造正确性结果或硬编码公开测试答案。

动态库加载不计时，因此不得在全局/静态构造函数、加载回调或其他
`sandpile_run` 之外的路径中初始化 CUDA、分配 GPU 资源、编译实现、处理
输入或预先计算输出。完成当前任务所需的全部工作必须发生在本次
`sandpile_run` 调用内。

除上述评测文件外，选手可以：

- 任意修改 `solution/` 下的源码和 `Makefile`；
- 增加自己的 `.h`、`.cuh`、`.cu`、`.cpp` 或其他文件；
- 自由选择稠密、稀疏、混合或其他合法稳定化算法；
- 使用 CUDA Toolkit 自带组件、C++ 标准库以及能够在统一环境中复现的额外依赖。

若使用题面未列出的库、编译器或工具，必须在 `optimization.md` 中写明名称、版本和安装方法。依赖不得要求外部在线服务或修改 GPU 驱动；无法按文档复现的提交不计入正式成绩。
